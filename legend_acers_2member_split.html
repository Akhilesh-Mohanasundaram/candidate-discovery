Split Logic

How the work
was divided

The original plan had 4 members. With 2, each person absorbs two complementary roles. The split follows a natural seam: Member A owns everything that requires AI intuition, semantic understanding, and evaluation judgment. Member B owns everything that requires systems engineering, performance, and user-facing deliverables.

A
Member A
AI Lead · Evaluation Lead

Owns the intelligence layer of the pipeline. Responsible for making the system understand the JD — not just match keywords. Owns all semantic scoring, ground-truth evaluation, reasoning generation, and LLM re-ranking. Also owns the honeypot detection logic design (the rules, not the code).

jd_parser.py scorer.py (semantic) reasoning_gen.py honeypot logic eval / ground truth LLM re-ranking
B
Member B
Systems Lead · Demo Lead

Owns the engineering backbone. Responsible for making the system fast, correct, and deliverable. Builds the feature engineering pipeline, behavioral multiplier, pre-computation script, submission validator, and the Streamlit demo. Code quality and runtime performance are critical path items.

feature_engineer.py behavioral.py honeypot.py (code) precompute.py rank.py sandbox/app.py README + docs
Pipeline Ownership

Stage-by-stage
ownership

Each stage has a clear owner. The "Responsibilities" column shows what that person builds and ships, not just reviews.

S1

JD Understanding & Decomposition

Parse the JD into hard requirements, soft preferences, explicit disqualifiers, and company-fit signals. Output: artifacts/jd_features.json. Everything else is blocked until this exists.

Member A — Write jd_parser.py. Extract HARD/SOFT/VETO tiers using rule-based NLP + regex. Build the semantic expansion ontology (e.g. "recommendation system" → retrieval). Test by printing the parsed JSON and verifying it makes intuitive sense.

A
S2

Honeypot & Trap Detection

Catch impossible profiles before scoring. All 7 trap types: experience > company age, expert skill with 0 months, 10+ expert skills, title-career mismatch, overlapping job timelines, skills not in career, keyword stuffer flag.

Member B writes honeypot.py (the code). Member A defines the detection rules and edge cases — then hands them to B as a written spec. B implements exactly what A specifies. Test on sample_candidates.json: verify zero false positives on clean candidates.

A+B
S3

Multi-Signal Feature Engineering

Extract 500+ features per candidate across 6 families: skill match, career history, education, disqualifier checks, location/logistics fit. Output: artifacts/feature_matrix.npz.

Member B owns feature_engineer.py entirely. Start with career_quality_score() on 5 sample candidates. Then add skill extraction, education tier weighting, and logistics scoring. Use chunked loading — never load all 100K into RAM at once.

B
S4

Hybrid Scoring Engine

Combine Semantic Skill Match (35%) + Career Quality (40%) + Logistics (10%) + Behavioral (15%). Apply VETO checks first — returns 0.0 immediately for disqualified profiles.

Member A owns the semantic scoring logic (MiniLM cosine similarity, proficiency × endorsement weighting) and the final scoring formula in scorer.py. Member B wires scorer.py end-to-end, integrates VETO checks, and runs it on the sample set first.

A+B
S5

Behavioral Signal Multiplier

Apply 23-signal availability formula as a multiplier (0.3–1.0) on raw scores. Penalizes inactive, unresponsive, or unavailable candidates — treats availability as a gate, not a bonus.

Member B owns behavioral.py entirely. Implement the recency decay formula (e^(–days/90)), recruiter response rate bonus, interview completion rate, and all 23 signal checks. Clamp output to [0.3, 1.0].

B
S6

Reasoning Generation + LLM Re-Rank

Generate specific, honest, non-templated reasoning per candidate for the CSV column. Optionally re-rank top 200 using Phi-3-mini GGUF. This is Stage 4 of judging — the reasoning column is manually reviewed.

Member A owns reasoning_gen.py entirely. Build the template system that inserts real candidate facts (title, YoE, top skills, location, notice period, response rate, career highlights, honest concerns). Attempt Phi-3-mini GGUF for top-200 if compute allows; template fallback is fine.

Coordination Rules

How to not
block each other

Two people means two critical dependencies. Manage them deliberately.

01

A unblocks B on Day 1

Member B cannot start scorer.py or feature_engineer.py until jd_features.json exists. Member A's first task is to ship jd_parser.py and commit the artifact. No waiting — Day 1.

02

B unblocks A on Day 2

Member A can't test semantic scoring end-to-end until B has the data loader and file skeletons up. B sets up the repo before anything else. A can then run their code against real data.

03

A writes rules, B writes code

For honeypot.py: A writes a precise written spec of all 7 detection conditions. B implements exactly that spec. Don't code from memory — hand the spec document over first.

04

Sample set first, always

Never run on full 100K until it works on the 50-candidate sample. The sample is fast — use it for all iteration. Full run only once you're confident in the logic.

05

A reviews every top-10

After every scoring change, Member A manually reviews the top-10 ranked candidates. They have the AI intuition to catch subtle bugs. B runs the code; A validates the output makes human sense.

06

B owns the submission

Member B runs validate_submission.py and is responsible for the final submission.csv being format-correct. A signs off on the reasoning quality. B signs off on the file format.

The Winning Edge

The architecture gets you into the top 20. The ground truth eval set (Member A's job) is what gets you to #1. Most teams skip this step. Build 20 manually-labeled candidates, score your system against them, and tune the weights until NDCG@10 is maximized. This is also what lets you defend your weight choices in the Stage 5 judge interview with specific data, not intuition.
